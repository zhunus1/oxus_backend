# R3: lifecycle доступа — исследование и минимальное решение

20.11.2026. **Реализация синхронного lifecycle не добавлялась:** её корректность зависит от неподтверждённого R1. Нет новых моделей, миграций, workers, фоновых задач или PostgreSQL-транзакций вокруг внешних запросов.

## Фактические точки изменения CRM

| Данные | Где меняются | Что происходит с Wazzup сейчас |
| --- | --- | --- |
| `assignedSalesManagerId` + `acceptedAt` | `SalesLeadRepository.accept`: одна условная `updateMany` для NEW/unassigned; далее запись активности в короткой транзакции | Синхронизации на accept нет; только на последующее открытие Wazzup |
| Новые phone/name/email | Ingestion repository и адаптеры landing/express/manual/legacy, ManualLeadV2Service | Создают Lead/LeadSubmission; не делают внешних вызовов |
| Телефон существующего Lead | Штатного HTTP endpoint изменения `Lead.phoneNumber` в проверенном коде не найдено; возможны административные SQL/import/seed и будущие операции | Следующее открытие использует новый номер, старые tokens не отзываются |
| Переназначение Sales существующего Lead | Штатного HTTP transfer endpoint в проверенном production-коде не найдено. Seed и прямые DB updates могут менять поле; сценарий воспроизведён DB-тестами | При следующем открытии нового владельца upsert по `lead-<id>`; немедленной синхронизации нет |
| Статусы лида/назначение Expert | Sales/Expert workflows и contract services | Не тождественны передаче Sales ownership; не должны самовольно переназначать Wazzup contact |
| Роль User | `AdminService.updateAdminUser` | После сохранения отзываются CRM sockets через `LeadRealtimeGateway.revokeUser`, не Wazzup sessions |
| Блокировка User | `AdminController.blockUser` | `deletedAt` + отзыв CRM sockets; Wazzup не уведомляется |
| Permissions Role и удаление Role | `RoleRepository.update`, `softDeleteMany` | Wazzup не уведомляется; новые ссылки проверяют актуальную БД |
| Permission definition/soft deletion | Admin permission module | Wazzup не уведомляется; WazzupService исключает удалённые permission |

Телефон из `PrepareLeadContractDto` относится к договору/создаваемому аккаунту студента; его нельзя автоматически считать изменением `Lead.phoneNumber`. `LeadRepository.markContacted` меняет legacy contacted fields, а не `assignedSalesManagerId/acceptedAt`.

## Доказанная граница текущего решения

Новая ссылка не выдаётся, если первоначальная или повторная проверка видит неактивного пользователя/роль, отсутствие permission, непринятый/чужой/удалённый лид или изменившийся телефон. Это проверено HTTP/реальной БД. Но в Wazzup уже выполненные writes не откатываются и существующий token/WS не зависит от нашего отказа вернуть новый URL.

Контрпример гонки:

1. A читает актуального owner A и проходит проверку.
2. Его `POST /contacts` уже отправлен, но применение задержано сетью/провайдером.
3. CRM передаёт лид B; запрос B выполняет upsert owner B.
4. Провайдер применяет запоздалый upsert A последним.
5. Повторная CRM-проверка запроса A возвращает 409, но удалённый owner уже A.

Локальный mutex только одного Node-процесса не защищает несколько инстансов и DB-изменения других модулей. Простое «поправить owner ещё одним POST» тоже может проиграть следующей гонке. Поле версии/If-Match/CAS у провайдера не документировано для используемого v3: оно не выдумывается в payload.

## Зависимость от R1

Сначала требуются доказанные свойства: момент удаления старого grant, действие на старый token/активный WS, read-back применённого owner и semantics замещения contactData. DELETE контакта по документации сохраняет диалог в общем окне, поэтому его нельзя считать достаточным revoke. Потеря связи с одним contact ID также не гарантирует отсутствие доступа через другой контакт/сделку того же номера.

Без этих свойств невозможно честно гарантировать «старый Sales потерял доступ» одной упорядоченной очередью upsert. Поэтому добавление Redis jobs/outbox/миграции сейчас не решило бы корневую проблему.

## Минимальный протокол после подтверждения провайдера

Это предложение, не реализованная гарантия:

1. Определить единицу доступа к WhatsApp: нормализованный телефон внутри конкретного Wazzup account/channel, а не произвольная заявка. Согласовать политику общих номеров.
2. Все writers этой единицы доступа должны участвовать в одном порядке операций между инстансами, включая CRM mutation и открытие окна. Использовать подтверждённый CAS провайдера либо обоснованный общий lock. Если нужен advisory lock, он должен быть session-level на выделенном соединении; не держать PostgreSQL transaction во время HTTP. TTL-lock без fencing сам по себе не исключает запоздалые writes.
3. До передачи действующего grant выполнить подтверждённый revoke старого доступа и проверить его. Не выдавать новую сессию при неопределённом результате. Затем сохранить CRM mutation короткой транзакцией и назначить только актуального владельца/телефон согласно проверенному протоколу.
4. После external write заново сверить authoritative CRM state и provider read-back перед выдачей ссылки. Не восстанавливать старый grant на основании устаревшего snapshot.
5. При 401/403/429/timeout не считать синхронизацию завершённой; запретить новые grants/links до контролируемого восстановления. Без durable состояния и подтверждённого revoke этот пункт не даёт автоматического self-healing — сначала проверить, достаточно ли ручного ограниченного reconciliation для test-этапа.
6. Только если доказано, что синхронный протокол не обеспечивает восстановление после падения процесса, отдельно обосновать durable journal/outbox. Это не автоматически разрешённая новая архитектура.

Порядок revoke/commit/grant и поведение при повторном создании user ID должны быть подтверждены поддержкой и live-тестом. Сейчас ни user-delete-on-every-open, ни автоматическое удаление контактов, ни смена всего API key не внедрены.

## Общие телефоны

Два лида одного Sales с одинаковым телефоном дают один chat filter, но два стабильных contact ID. Разные Sales с одним телефоном не получают две независимые WhatsApp-истории: это одна переписка. Потребуется явное решение: общий доступ к этому клиенту либо единственный ответственный. Минимальный fail-closed вариант до решения — не выдавать Sales-доступ к неоднозначно принадлежащему номеру; корректная проверка должна учитывать нормализацию исторических форматов, не только строковое равенство.

Не заменять `lead-<id>` на contact ID по телефону без согласованного перехода: старые contact records останутся и могут сохранять grants. Массовая очистка данных в рамках этой работы не выполняется.

**Статус R3: BLOCKED BY R1 + бизнес-политика общих номеров.** Для кода с выключенным Wazzup внешних writers нет; это делает OFF-размещение допустимым при выполнении release-условий, но не закрывает R3 для включённой интеграции.
