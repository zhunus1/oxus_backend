### Блокирующие вопросы провайдера

**R1 — отзыв старых сессий, HIGH / NOT VERIFIED.** User API v3 iframe описывает выпуск URL, но в изученной документации не описаны гарантированный индивидуальный revoke и синхронная блокировка открытых websocket-сессий после изменения CRM permission. Удаление пользователя API документировано, но обещания отзыва ранее выданного iframe нет. Реальная API-проверка получила ссылку; декодированный, криптографически не проверенный payload token содержит `exp - iat = 28800` секунд (8 часов). Это наблюдение одного токена, а не подтверждённый SLA TTL или верхний предел жизни открытой сессии. Удаление технического пользователя подтвердилось 200/404; доступа к переписке после удаления не проверяли и успешный revoke не заявляем.

Следствие: сохранённая ссылка или уже открытое соединение могут сохранить доступ после переназначения, деактивации или понижения ADMIN до Sales. Backend не передаёт эти изменения Wazzup автоматически. Закрытие iframe, новый CRM JWT и отказ выдавать новую ссылку старую сессию не аннулируют.

Минимум для снятия блокера: подтверждённый Wazzup механизм отзыва/изменения эффективных прав, проверенный на активной и повторно открытой сессии; затем привязка этого механизма к отзыву CRM permission, роли/аккаунта и передаче лида. Если v3 не даёт такого механизма, безопасный первый этап требует отдельного решения об ограничении/отключении Sales-доступа; объявлять текущую реализацию полностью безопасной нельзя. Не добавлены выдуманные API endpoints, параметры TTL или непроверенный переход на Partner API.

**R2 — реальная изоляция Sales в Wazzup, HIGH / NOT VERIFIED.** Наличие server-side `filter` и корректный DB scope подтверждены. Но документация определяет filter как набор отображаемых чатов, а не формальное доказательство авторизации всех внутренних запросов. Две реальные Wazzup-сессии с назначенными ролями «Менеджер», собственными техническими контактами, поиском, навигацией и попыткой доступа к чужому chat ID не проверены. В начале реального аудита пользователей и контактов в тестовом аккаунте было 0. Настройки канала не менялись; production данные не создавались.

Минимум: контролируемый live-тест двух технических Sales и ADMIN на отдельном аккаунте, включая общее окно, поиск, чужой чат, смену owner и отзыв прав. Роль «Менеджер» у Sales в Wazzup обязательна; роль «Руководитель» нельзя компенсировать скрытыми UI-кнопками. Пользовательский API v3 не документирует настройку ролей; Partner API v2 имеет другой auth и в эту интеграцию не подмешивался.

**R3 — lifecycle внешних контактов и гонки, HIGH / OPEN.** Upsert происходит по запросу открытия. Изменение телефона/owner само по себе не удаляет старые внешние связи и не синхронизирует отзыв доступа. Запоздалый upsert A способен перезаписать внешнего ответственного после более нового upsert B; последующая перепроверка заблокирует ответ A, но не откатит уже применённое внешнее изменение. На одной проверке `assignedSalesManagerId` нельзя строить утверждение о полном lifecycle isolation. Для устранения нужен согласованный с R1 механизм синхронизации и отзыва, а не локальный mutex одного процесса или длинная DB-транзакция вокруг внешнего API.

### Контакты и номера

При повторной синхронизации одного лида ID `lead-<id>` сохраняется, поэтому payload не создаёт новый ID при каждой попытке. Изменение phone/owner передаётся под тем же ID при следующем открытии; это проверено payload-тестами. Реальный contacts upsert не выполнялся: live-аудит не менял контакты. Свойства удаления старых связей номера и применения смены owner в работающем iframe поэтому не подтверждены реальным API.

Отдельные лиды с одинаковым телефоном имеют разные Wazzup contact IDs. Дедуплицируется фильтр чатов, а не вся удалённая contact database. WhatsApp переписка относится к номеру: разделить историю одного номера по независимым CRM-лидам нельзя обещать. Для разных Sales с одним номером нужна явная политика бизнес-доступа; не добавлялись новая Contact-модель, массовая очистка или миграция существующих данных.

## Что конкретно блокирует push

1. Подтверждённый отзыв/ограничение ранее выданных iframe-сессий при изменении CRM-доступа, включая уже открытое соединение.

3. Согласованное исправление lifecycle внешнего owner/телефона и гонки upsert, а не только запрет новой ссылки.
4. Общий private Document API gate не зелёный: на текущих изменениях 5 transport failures, на чистом HEAD 3 аналогичных. Это воспроизведённая исходная нестабильность вне Wazzup, которую нельзя маскировать или считать PASS перед выпуском.

Повторная выдача URL, периодический frontend refresh, закрытие iframe при logout и unit mocks не закрывают эти пункты. Без их закрытия ответ на «можно ли сейчас пушить безопасно готовый backend в test?» — **нет**.
