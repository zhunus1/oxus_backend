# Wazzup: первый этап интеграции

Реализован backend для окна чатов Wazzup: чат в карточке лида, общий список чатов, проверка подключённых каналов. Доступ разрешён ADMIN и SALES_MANAGER. EXPERT и клиентские роли доступа не имеют. Существующие API, схема БД, Twilio, OTP и уведомления не меняются.

**Текущий статус:** выключенный backend — CONDITIONAL GO после проверки server OFF и CI; включение реальным сотрудникам — NO-GO. Live-проверка отложена до test server по решению владельца. [Актуальное ревью](FOLLOWUP.md), [подготовка выкладки и команды](RELEASE.md), [вопросы поддержке и live-протокол](PROVIDER_VALIDATION.md), [lifecycle](LIFECYCLE.md), [Document transport](DOCUMENT_TRANSPORT.md).

## Настройка отдельного тестового аккаунта

Следующие шаги описывают будущую согласованную техническую проверку, а не текущее разрешение включить интеграцию. Для размещения кода оставить `WAZZUP_ENABLED=false`; роль в Wazzup и доступ к каналу менять только в согласованном тестовом окне.

1. В новом аккаунте Wazzup подключить тестовый WhatsApp и подписку. Не подключать этот аккаунт к amoCRM/Битрикс24: нужен полный API-ключ, а не Sidecar. Номер аккаунта из старой переписки в коде не используется.
2. В локальном `.env` или серверном `deployment/.env` установить `WAZZUP_ENABLED=true`, `WAZZUP_API_KEY=<полный ключ нового аккаунта>`. Хранить ключ только на backend. По умолчанию интеграция выключена; без ключа endpoint вернёт 503 `WAZZUP_NOT_CONFIGURED`.
3. Перезапустить backend с обновлённым окружением. Обе Compose-конфигурации передают эти настройки. При изменении окружения уже запущенного контейнера его нужно пересоздать.
4. Под JWT администратора вызвать `GET /api/v1/integrations/wazzup/channels`. Проверить нужный номер и `state=active`. Для обычного WhatsApp `transport=whatsapp`, для WABA — `wapi`. Успешный запрос каналов сам по себе ещё не подтверждает доступ к полному API.
5. При необходимости указать `WAZZUP_CHANNEL_ID=<channelId>`: он выбирает активный канал при открытии карточки. Это не ограничение доступа к остальным каналам аккаунта; тест и production должны использовать разные аккаунты.
6. Вызвать endpoint окна под нужными CRM-пользователями. Backend добавляет/обновляет пользователя Wazzup с `id`, равным строковому `User.id`, и актуальным именем из БД. В кабинете Wazzup настроить этим сотрудникам доступ к тестовому каналу: ADMIN — «Руководитель», Sales — «Менеджер». Публичный API пользователей не документирует установку этих ролей; они не передаются как выдуманное поле API. Если первое окно пустое, проверить эти настройки и запросить новую ссылку.

Старт приложения не вызывает внешний API. В этой реализации нет отправки сообщений отдельным API-методом, массовых рассылок, подписки на вебхуки, создания лидов из входящих сообщений и фоновой полной синхронизации. Переписка идёт через встроенный интерфейс Wazzup.

## API для frontend

Все endpoints требуют действующий CRM JWT (Bearer или штатная cookie). Ссылки содержат сессионный токен Wazzup: не записывать их в аналитику, логи, localStorage или общий кеш. Backend возвращает `Cache-Control: no-store`.

| Запрос | Доступ | Ответ |
| --- | --- | --- |
| `GET /api/v1/integrations/wazzup/channels` | ADMIN | Массив `{ channelId, transport, plainId, state }` |
| `POST /api/v1/integrations/wazzup/iframe` | ADMIN, Sales | `{ "url": "https://…wazzup24.com/chat/…?token=…" }` |
| `POST /api/v1/integrations/wazzup/leads/:id/iframe` | ADMIN, владелец лида Sales | `{ "url": "…" }` |

POST-запросы не требуют тела. Пользователь, роль, список чатов и телефон определяются сервером; присланные клиентом значения не используются. Телефон берётся из `Lead.phoneNumber`, нормализуется штатной функцией проекта и передаётся в Wazzup без `+` и разделителей. Удалённые лиды исключены; Sales сначала должен принять лид.

Для ADMIN общий endpoint использует Wazzup `scope=global`. Для Sales он использует `scope=card` со списком телефонов закреплённых CRM-лидов: это общий список своих клиентов, а не неограниченное окно Wazzup. Так в окно не попадают новые неназначенные обращения аккаунта. Перед выдачей Sales-ссылки контакты добавляются/обновляются в Wazzup пакетами до 100 записей, с ID `lead-<Lead.id>` и ответственным текущим Sales. Открытие карточки администратором не переназначает контакт.

Для Sales дополнительно проверяются принятие лида (`acceptedAt != null`) и действующее право `SALES_LEADS_MANAGE_OWN`. Роль и права берутся из текущей БД, не из заявленной роли JWT. Одинаковые телефоны объединяются в один элемент фильтра чатов: переписка WhatsApp относится к номеру, а не к отдельной заявке. Контакты Wazzup имеют ID по лидам; разные заявки на один номер могут оставаться разными контактами.

Frontend запрашивает свежую ссылку при открытии окна и вставляет её в:

```html
<iframe src="URL_FROM_BACKEND" allow="microphone *; clipboard-write *"></iframe>
```

Размеры и кнопку открытия задаёт frontend. Если frontend использует CSP `frame-src`, разрешить аккаунтный HTTPS-домен Wazzup из ответа. При закрытии окна удалять iframe; при выходе из CRM также закрывать его.

| Статус / code | Значение |
| --- | --- |
| 400 / `WAZZUP_INVALID_PHONE` | У лида нет корректного телефона |
| 400 | Некорректный ID лида |
| 401 / 403 | Нет доступа в CRM |
| 404 | Лид не найден, удалён или принадлежит другому Sales |
| 409 / `WAZZUP_NO_CHATS` | Нет закреплённых лидов с корректными телефонами; показать пустое состояние |
| 409 / `WAZZUP_CHAT_LIMIT` | Более 1000 закреплённых лидов с заполненными телефонами; доступно открытие отдельной карточки |
| 409 / `WAZZUP_ACCESS_CHANGED` | Права на лид или телефон изменились в процессе открытия; обновить карточку |
| 502 / `WAZZUP_ACCESS_DENIED` | Wazzup вернул 401/403; проверить ключ, полный API и права интеграции |
| 502 / `WAZZUP_UPSTREAM_ERROR`, `WAZZUP_INVALID_RESPONSE` | Ошибка или неожиданный ответ провайдера |
| 503 / `WAZZUP_NOT_CONFIGURED`, `WAZZUP_RATE_LIMITED` | Интеграция выключена/не настроена или лимит запросов Wazzup |
| 503 / `WAZZUP_CHANNEL_UNAVAILABLE` | Нет активного WhatsApp/WABA либо настроенный канал недоступен |
| 504 / `WAZZUP_TIMEOUT` | Запрос к провайдеру превысил 10 секунд |

Нет автоматических повторов запросов. Внешние запросы открытия имеют общий бюджет 30 секунд и timeout 10 секунд на запрос. Канал проверяется до внешних записей. При ошибке синхронизации контактов ссылка не выдаётся. Роль/permission, актуальность владельца, принятие и телефон перепроверяются до записей, перед запросом ссылки и перед возвратом её клиенту. Это не распределённая транзакция и не отзыв сессии. Ответы провайдера, Axios-конфигурация и секреты не возвращаются клиенту и не пишутся в лог ошибок.

## Проверка на новом аккаунте

Автотесты не используют реальные ключи и не отправляют сообщения:

```bash
yarn build
yarn test --runInBand --runTestsByPath src/modules/wazzup/wazzup.client.spec.ts src/modules/wazzup/wazzup.service.spec.ts src/modules/wazzup/wazzup.controller.spec.ts
```

После настройки ключа проверить вручную:

1. ADMIN получает каналы и открывает общий виджет; `POST /users` и `POST /iframe` проходят без 403.
2. Создать двух Sales с разными закреплёнными тестовыми лидами. Под каждым открыть карточку и общий список: в окне только его номер; другой лид и неназначенный лид дают 404. Проверить также ограничения внутри самого iframe, включая поиск чатов.
3. Проверить пустое состояние у Sales без закреплённых лидов и отсутствие доступа у EXPERT.
4. Отправить одно согласованное тестовое сообщение через виджет и получить ответ. Проверить голосовое сообщение/копирование при необходимости.
5. ADMIN открывает чужую карточку, после чего ответственный контакта в Wazzup остаётся Sales.

## Границы первого этапа

Список доступных телефонов фиксируется при выпуске ссылки. Уже открытая сессия контролируется Wazzup: backend не отзывает её при смене роли, удалении пользователя или изменении ответственного. Перед production нужны проверка срока жизни/отзыва сессий у Wazzup и синхронизация удаления/переназначения контактов; особенно если появятся новые операции передачи Sales-лидов. Доступ сотрудников через самостоятельное приложение Wazzup отдельно этим backend не управляется.

Синхронизация выполняется по запросу, а не непрерывно. Новые лиды в открытом окне появятся после его повторного открытия; полная история/названия контактов для ADMIN могут потребовать отдельной начальной синхронизации. Для более 1000 лидов у одного Sales пока предусмотрено открытие карточки; пагинация общего окна — отдельный следующий шаг.

Для следующего этапа: обработка защищённых идемпотентных вебхуков, входящие обращения и распределение лидов, синхронизация жизненного цикла пользователей/контактов, затем автоматические сообщения по событиям воронки с очередью и контролем повторов.
