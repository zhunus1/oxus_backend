# Wazzup R1/R2: вопросы и план проверки на test

20.11.2026. По решению владельца проекта полноценная live-проверка двух Sales **перенесена на test server**. Здесь подготовлен сценарий; он не выполнен и не является разрешением включить интеграцию реальным сотрудникам. Сообщение поддержке подготовлено, но не отправлено.

## Что установлено

User API v3 документирует выпуск iframe URL, upsert/delete пользователей, upsert/delete контактов. Документированной гарантии индивидуального revoke iframe, немедленного прекращения активного WebSocket и SLA TTL в просмотренных разделах не найдено. Это означает «не подтверждено», а не «невозможно».

Первичный live-аудит подтвердил выпуск ссылки и удаление отдельного технического пользователя (200, затем GET 404). Token payload содержал `exp - iat = 28800` секунд; подпись, серверное соблюдение TTL и судьба активного соединения не проверены. Удаление пользователя не засчитывается как revoke test.

Повторная текущая проверка — только read-only: API key действителен, `/channels`, `/users`, `/contacts` отвечают 200; сотрудников и контактов пока 0. Отдельная проверка заведомо неправильного ключа возвращает 401. Новые сотрудники, контакты, сессии и сообщения в этой проверке не создавались.

Удаление контакта не гарантирует исчезновения диалога: документация прямо сообщает о сохранении диалога в общем окне. Поэтому `DELETE /contacts/:id` не используется как неподтверждённый способ отзыва доступа.

## Готовый текст обращения в поддержку

Здравствуйте! Мы разрабатываем непубличную интеграцию собственной CRM OXUS с Wazzup через **User API v3**, используя полный API key отдельного тестового аккаунта. Используем `POST /v3/users`, `POST /v3/contacts`, `POST /v3/iframe`. Sales работают с ролью «Менеджер», ADMIN — «Руководитель». Требуется гарантированно отзывать доступ при смене ответственного, роли или CRM permission.

Просим подтвердить поведение именно User API v3:

1. Есть ли поддерживаемый метод отзыва конкретной ранее выданной iframe-ссылки/token либо всех сессий указанного CRM user ID? Нужны точные method/path/body, ограничения и коды ответа.
2. Что гарантирует `DELETE /v3/users/:id`: запрет только новых ссылок, запрет повторного открытия старой ссылки, прекращение уже открытого iframe, закрытие существующих WebSocket? Какова максимальная задержка применения?
3. Если пользователя с тем же CRM ID создать снова, смогут ли ранее выданные tokens снова получить доступ? Как безопасно восстановить сотрудника без восстановления старых сессий?
4. Проверяется ли актуальная роль/привязка контакта на каждом чтении истории, поиске, отправке, получении сообщений через уже открытый WebSocket? Или права фиксируются при выпуске ссылки/соединении?
5. Какой гарантированный TTL iframe-token и активного соединения? Можно ли задать более короткий TTL через v3? В одном ответе мы наблюдали 8 часов в token claims, но не считаем это договорной гарантией.
6. Является ли `scope=card + filter` обязательным серверным ограничением запросов истории/поиска/отправки и WebSocket subscriptions, либо только фильтром отображения? Можно ли из такой сессии получить историю chat ID, не входящего в filter?
7. При upsert контакта с тем же `id` и новым `responsibleUserId` когда старый ответственный теряет доступ, включая текущие окна? Сохраняется ли доступ через другие контакты/сделки с тем же номером?
8. Замещает ли новый `contactData` прежние телефоны, либо объединяется с ними? Как отозвать старую связь телефона, не удаляя историю и не делая диалог доступным менеджерам как «новому клиенту»?
9. Есть ли в v3 операции ролей/доступов, read-back применённых прав и контроль версии/CAS для упорядочивания параллельных upsert? Каков безопасный порядок revoke → transfer → grant при сетевом timeout с неопределённым результатом?
10. Можно ли гарантированно синхронизировать отзыв CRM permission с Wazzup без замены ключа всего аккаунта и без затрагивания других сотрудников? Если нет, какой поддерживаемый сценарий рекомендуется?

Partner API v2/OAuth мы не подключаем. Просим не предлагать его методы как совместимые с нашим v3 API key без явного подтверждения авторизации и условий перехода. Секретный API key в обращение не включён.

## Условия запуска live-проверки

- Backend размещён на test, исходно `WAZZUP_ENABLED=false`, пройдены OFF smoke и CI.
- Отдельный тестовый Wazzup account; не production и не аккаунт действующей amoCRM/Битрикс.
- Два **контролируемых** WhatsApp recipient номера A/B с технической историей; номера реальных клиентов, случайные номера и сам номер канала не используются вместо двух независимых контактов.
- В тестовой CRM созданы технические ADMIN, Sales A/B, два принятых лида с различными телефонами; у обоих Sales действующий `SALES_LEADS_MANAGE_OWN`.
- В Wazzup только техническим сотрудникам на согласованном тестовом канале выданы роли: Sales A/B — «Менеджер», ADMIN — «Руководитель». Назначение ролей относится к настройкам канала и требует отдельного разрешения; существующие настройки самовольно не меняются.
- Подготовлены три изолированных браузерных профиля, безопасное временное хранение tokens только в памяти и возможность наблюдения за WebSocket. HAR с tokens/содержимым сообщений в репозиторий не сохраняется.
- Доступ к real API key остаётся только на test backend; перед включением известен ответ поддержки или явно обозначены ещё непроверенные гипотезы.

Сейчас недостающие условия: test server ещё не развёрнут этим агентом; A/B recipient номера и технические сотрудники с подтверждёнными ролями не предоставлены; согласование изменения channel roles и ответы поддержки отсутствуют. Поэтому полноценные R1/R2 эксперименты сейчас **NOT RUN / DEFERRED BY USER**.

## Протокол live-проверки

| Шаг | Действие | Обязательное доказательство |
| --- | --- | --- |
| 1 | В OFF-режиме вызвать Wazzup endpoints под действующими ADMIN/Sales | 503 `WAZZUP_NOT_CONFIGURED`, нет URL и внешних calls |
| 2 | В согласованном окне включить только тестовую интеграцию | Нужный account/channel; остальные окружения остаются OFF |
| 3 | Открыть карточку A под Sales A, B под Sales B | Собственный чат доступен; HTTP A→B и B→A — 404 |
| 4 | Открыть общий интерфейс обоих Sales | Только свои номера и техническая история |
| 5 | Проверить поиск, навигацию и попытку чужого chat ID внутри каждого iframe | Нет чужой истории, файлов, unread данных, сообщений или subscriptions; одного скрытого UI-элемента недостаточно |
| 6 | Открыть оба контакта под ADMIN | История доступна; GET contacts до/после подтверждает неизменность ответственных |
| 7 | Сохранить token A только в памяти, оставить iframe/WebSocket A открытым; переназначить лид A на Sales B | Отдельно проверить отказ новой CRM-ссылки A и поведение прежнего token/соединения |
| 8 | Удалить у Sales A CRM permission | Новые links запрещены; старые HTTP/WS не получают защищённые данные после подтверждённого revoke |
| 9 | Поддерживаемым способом удалить технического Wazzup user A | Проверить повторное открытие старой ссылки в чистом браузере и старое уже открытое соединение |
| 10 | Только по согласованному протоколу восстановить тот же user ID | Старый token не должен незаметно ожить |
| 11 | Проверить фактическое истечение TTL и повторное подключение | Авторизационный отказ после срока, а не только декодированное поле `exp` |
| 12 | Проверить transfer/phone replacement и одинаковый номер у двух лидов | Read-back owner/phone и реальные права каждого окна соответствуют согласованной политике |

Для активного WebSocket нужен наблюдаемый контроль: техническое событие/сообщение, разрешённое между контролируемыми тестовыми номерами. Просто отсутствие нового трафика не доказывает revoke. Отправку согласовать в этом протоколе отдельно; реальные клиенты исключены.

HTTP 200 HTML shell, iframe `load`, успешный `POST /iframe`, GET user 404 и закрытие окна самим frontend **не являются доказательством прекращения доступа к истории/отправке/WS**. Для каждого случая фиксировать времена (UTC), HTTP-коды, WS close/error, доступность только технических canary данных и воспроизводимость после reconnect. Значения key/token и реальная переписка не входят в отчёт.

При обнаруженной утечке остановить проверку и выключить backend-флаг; отдельно выполнить подтверждённый provider revoke. Сам `WAZZUP_ENABLED=false` старые provider tokens не отзывает. Удалять после теста только явно созданные технические сущности; настройки реального канала, подписка и ключ всего аккаунта не меняются.
