# Wazzup: контракт подключения frontend

Проверено по реализации 20.11.2026. Документ описывает существующий HTTP-контракт. Актуальное решение — в [FOLLOWUP.md](FOLLOWUP.md): размещение с выключенным Wazzup — CONDITIONAL GO после server OFF/CI; включение сотрудникам — NO-GO. Live-проверка перенесена владельцем проекта на test server. Frontend в рамках ревью не менялся.

При выключенном Wazzup разрешённый запрос возвращает 503 `WAZZUP_NOT_CONFIGURED`, ссылка не выдаётся. UI не должен предлагать сотрудникам рабочие чаты до отдельного включения и проверки [R1/R2](PROVIDER_VALIDATION.md). Закрытие iframe, logout CRM и backend-флаг OFF не являются подтверждённым отзывом уже выданной provider-сессии.

## Авторизация и роли

Базовый путь: `/api/v1/integrations/wazzup`. Поддерживаются штатная cookie `accessToken` и `Authorization: Bearer <CRM_ACCESS_TOKEN>`. Для cross-origin cookie-запросов использовать существующую конфигурацию CRM с `credentials: "include"` и разрешённым CORS-origin. Ключ Wazzup никогда не передаётся frontend.

Backend читает текущую роль, состояние аккаунта и permissions из БД. Значение `roleCode` в JWT не даёт повышенных прав. Для Sales обязательно действующее право `SALES_LEADS_MANAGE_OWN`; удалённое permission также не считается действующим.

| Endpoint | ADMIN | SALES_MANAGER | EXPERT и остальные |
| --- | --- | --- | --- |
| `GET /channels` | Разрешён | 403 | 403 |
| `POST /iframe` | Общее окно в пределах прав Wazzup | Только телефоны своих принятых лидов | 403 |
| `POST /leads/:id/iframe` | Любой неудалённый лид | Только свой принятый неудалённый лид | 403 |

«Принят» означает `Lead.acceptedAt != null`, «свой» — `Lead.assignedSalesManagerId == currentUser.id`. Назначения без `acceptedAt` недостаточно. Допустимы разные бизнес-статусы лида; endpoint не меняет их и не принимает лид автоматически.

## 1. Список каналов

```http
GET /api/v1/integrations/wazzup/channels
Authorization: Bearer <CRM_ACCESS_TOKEN>
```

Параметры и тело отсутствуют. Успех — HTTP 200:

```json
[
  {
    "channelId": "11111111-2222-4333-8444-555555555555",
    "transport": "whatsapp",
    "plainId": "12025550100",
    "state": "active"
  }
]
```

Это иллюстративные значения. Ответ может быть пустым массивом. Endpoint возвращает каналы аккаунта разных типов; он не фильтрует только WhatsApp и не раскрывается Sales. Доступность самого окна проверяется отдельно: нужен активный `whatsapp` или `wapi`, совпадающий с `WAZZUP_CHANNEL_ID`, если тот задан. WABA использует `transport=wapi`, но чаты по телефону — `chatType=whatsapp`.

## 2. Чат в карточке лида

```http
POST /api/v1/integrations/wazzup/leads/123/iframe
Authorization: Bearer <CRM_ACCESS_TOKEN>
```

Тело не требуется. `id` — целое от 1 до 2147483647. Не передавать телефон, пользователя или роль: backend получает их из БД и не использует одноимённые поля тела запроса.

Успех — HTTP 200:

```json
{
  "url": "https://12345678.wazzup24.com/chat/example?token=SESSION_TOKEN"
}
```

Номер берётся из `Lead.phoneNumber`, а не из объекта пользователя. Backend нормализует его штатной функцией, дополнительно исключает ведущий ноль кода страны и передаёт Wazzup цифры без `+`. Некорректный исторический номер даёт 400. Новый телефон синхронизируется при следующем открытии под тем же контактным ID `lead-<id>`.

Для Sales перед открытием upsert сотрудника и контакта выполняется в Wazzup. ADMIN не отправляет upsert контакта с собой как ответственным; существующий владелец не переназначается. Провайдер может автоматически создать ранее отсутствующий контакт при открытии `scope=card` — гарантии отсутствия любых новых сущностей на стороне Wazzup нет.

## 3. Общее окно

```http
POST /api/v1/integrations/wazzup/iframe
Authorization: Bearer <CRM_ACCESS_TOKEN>
```

Тело не требуется. Успешный ответ тот же: HTTP 200, `{ "url": "..." }`.

ADMIN получает Wazzup `scope=global`. Sales получает `scope=card` с явным списком телефонов закреплённых принятых лидов. Пустой список никогда не превращается в неограниченное окно. Одинаковые нормализованные телефоны объединяются в один элемент фильтра. Контакты Wazzup при этом имеют ID по лидам: разные лиды могут создавать разные контакты с одним номером.

Окно Sales ограничено 1000 принятых неудалённых лидов с `phoneNumber != null`, включая исторические строки с некорректным непустым телефоном. Превышение даёт 409 `WAZZUP_CHAT_LIMIT`; доступна отдельная карточка. При отсутствии корректных телефонов — 409 `WAZZUP_NO_CHATS`. Изменение набора лидов учитывается при повторном открытии окна.

## 4. Использование ссылки

```html
<iframe
  src="URL_FROM_BACKEND"
  allow="microphone *; clipboard-write *"
  referrerpolicy="no-referrer"
></iframe>
```

Размеры определяются CRM. Назначать `src` через свойство компонента/DOM, не собирать HTML через `innerHTML`. При CSP разрешить нужный HTTPS-домен Wazzup в `frame-src`. Не менять URL и не извлекать token для собственных запросов. Backend уже проверяет HTTPS, домен `.wazzup24.com`, отсутствие встроенного логина/пароля/нестандартного порта и наличие token.

Ссылка содержит доступ к сессии. Хранить её только в памяти текущего окна. Не включать в URL CRM, аналитику, логи ошибок, localStorage/sessionStorage и общий query-cache. Ответы endpoint имеют `Cache-Control: no-store`; iframe-ответы также имеют `Pragma: no-cache`. Не разделять ссылку между сотрудниками. Запрашивать новую при новом открытии.

При закрытии окна, выходе из CRM и изменении роли удалять iframe и ссылку из памяти. Это мера поведения UI, а не доказанный отзыв сессии у провайдера. Закрытие iframe не аннулирует сохранённую копию ссылки.

## 5. Ошибки

Ответы имеют две формы. Доменные ошибки Wazzup содержат `code` и `message`, например:

```json
{
  "code": "WAZZUP_ACCESS_CHANGED",
  "message": "Lead access or phone changed; reopen the chat window"
}
```

Стандартные ошибки Nest/guards содержат HTTP-статус, например:

```json
{
  "message": "Lead not found",
  "error": "Not Found",
  "statusCode": 404
}
```

Использовать HTTP-статус и `code`, когда он есть; не сравнивать английский `message`. Не рассчитывать, что `statusCode` или `code` присутствуют во всех ответах. Общие парсерные ошибки и ограничения размера JSON остаются стандартными ошибками CRM; POST не требует тела.

| HTTP | `code`, если есть | Поведение frontend |
| --- | --- | --- |
| 400 | `WAZZUP_INVALID_PHONE` либо стандартная ошибка ID | Показать проблему с телефоном/параметром; не повторять автоматически |
| 401 | стандартная ошибка auth | Применить штатный механизм восстановления CRM-сессии или входа |
| 403 | стандартная ошибка роли/permission | Удалить iframe, показать отсутствие доступа |
| 404 | стандартная ошибка `Lead not found` | Карточка отсутствует, удалена, не принята или принадлежит другому Sales; не раскрывать причину |
| 409 | `WAZZUP_NO_CHATS` | Пустое состояние: нет доступных контактов |
| 409 | `WAZZUP_CHAT_LIMIT` | Предложить открыть чат из карточки |
| 409 | `WAZZUP_ACCESS_CHANGED` | Права/владелец/телефон изменились в ходе открытия; обновить карточку, повторять только по действию пользователя |
| 502 | `WAZZUP_ACCESS_DENIED` | Проблема ключа/прав интеграции у провайдера; это не истечение JWT сотрудника |
| 502 | `WAZZUP_UPSTREAM_ERROR`, `WAZZUP_INVALID_RESPONSE` | Показать временную ошибку интеграции; ручной повтор |
| 503 | `WAZZUP_NOT_CONFIGURED` | Интеграция выключена или не задан ключ |
| 503 | `WAZZUP_CHANNEL_UNAVAILABLE` | Нет активного подходящего WhatsApp-канала либо настроенный канал недоступен |
| 503 | `WAZZUP_RATE_LIMITED` | Лимит провайдера; не запускать бесконечные повторы |
| 504 | `WAZZUP_TIMEOUT` | Таймаут внешнего API; предложить ручной повтор |

`GET /channels` может вернуть 401/403/502/503/504; пустой массив там является успехом. Ошибки 400/404 относятся к карточке, а `WAZZUP_NO_CHATS` и `WAZZUP_CHAT_LIMIT` — к общему окну Sales.

## 6. Состояния интерфейса

1. По клику показать loading и заблокировать повторный клик. Не создавать запросы при каждом render. Один запрос может включать preflight каналов, upsert сотрудника и несколько пакетов контактов.
2. При 200 установить `src`. Получение URL не доказывает готовность интерфейса Wazzup: iframe ещё должен загрузиться, а сотруднику нужны права канала в Wazzup. Событие iframe `load` тоже не является доказательством доступа к чатам.
3. При ошибке убрать прежний iframe, обработать статус по таблице. 409 `WAZZUP_NO_CHATS` — отдельное пустое состояние.
4. При закрытии отменить ожидание запроса и очистить UI. Отмена frontend-запроса не гарантирует отмену уже начатого запроса к Wazzup.

Backend ограничивает один HTTP-запрос к Wazzup 10 секундами и цепочку внешних запросов открытия примерно 30 секундами общим AbortSignal. Проверки БД не имеют отдельного 30-секундного HTTP-дедлайна. Автоматических повторов у backend нет.

Для ADMIN доступны общая кнопка чатов, кнопка в любой неудалённой карточке и административный просмотр каналов. Для Sales — общая кнопка своих чатов и кнопка в собственной принятой карточке при наличии permission. Для остальных ролей элементы Wazzup скрыть; безопасность обеспечивается backend независимо от скрытия UI.

## 7. Настройки и обязательные ограничения

- Backend: `WAZZUP_ENABLED=true`, полный `WAZZUP_API_KEY`, при необходимости `WAZZUP_CHANNEL_ID`. На сервере используется `deployment/.env`; локальный `.env` туда автоматически не переносится.
- Раздельные аккаунты Wazzup для теста и production. `WAZZUP_CHANNEL_ID` выбирает/проверяет канал, но не является изоляцией других каналов общего аккаунта.
- Wazzup: активная подписка и канал; CRM `User.id` передаётся строкой. После появления сотрудника настроить на канале ADMIN как «Руководитель», Sales как «Менеджер». Нельзя давать Sales роль руководителя в расчёте на скрытые frontend-кнопки.
- Входящие обращения, воронки, вебхуки, рассылки и создание CRM-лидов из Wazzup в этой реализации отсутствуют. Они не должны имитироваться frontend-событиями.
- Перед выпуском требуется подтвердить реальную изоляцию Sales и отзыв старых сессий. Тесты HTTP-контракта и наличие фильтра не подтверждают поведение открытой переписки у провайдера.
