# Локальные резервные копии Test и Production

Один скрипт обслуживает существующий стек `oxus_backend` на обоих серверах,
каталог проекта `/opt/oxus_backend/deployment`. Локальные копии создаются на обоих
серверах; облачная выгрузка запланирована отдельным этапом только для Production
и пока не настроена.
Копии на том же сервере не переживут потерю сервера или его диска.
При ежедневном расписании можно потерять до суток данных; при пропусках — больше.

| Окружение | SSH host | Проверка приложения | Локальный каталог |
| --- | --- | --- | --- |
| `production` | `87.106.144.28` | `STAGING=false` | `/var/backups/oxus-backend/production` |
| `test` | `test.oxusedu.com` (`217.154.218.174`) | `STAGING=true` | `/var/backups/oxus-backend/test` |

Ни данные, ни секреты между серверами не копируются. Параметр `--environment`
проверяется перед остановкой API и записывается в манифест и журнал восстановления.
Неверное окружение блокирует запуск. Для совместимости команда без параметра
`--environment` выбирает `production`; установщик всегда требует явный выбор.

## Расписание и состав

Запуск на обоих серверах каждый день в **00:00 Asia/Almaty**, независимо от часового пояса ОС.
После дневного включения сервера пропущенная копия автоматически не запускается:
это сохраняет согласованное ночное окно недоступности. Повторных попыток в течение
дня нет. Если deployment держит общий `.deploy.lock`, бэкап завершится ошибкой.

Во время копирования останавливаются исходные контейнеры backend и MinIO.
PostgreSQL, Redis и Chrome продолжают работать. Сжатие MinIO, проверка архивов,
хеширование и удаление устаревших копий выполняются после возврата API.
В манифесте сохраняется фактически измеренная длительность остановки.
Ориентир для измеренных небольших данных Production — 1–2 минуты, до первого запуска это оценка.
Бюджет копирования — около 120 секунд, затем выполняется возврат сервисов;
проверки здоровья и задержки диска могут увеличить общее время недоступности.

Каждая завершённая точка содержит:

| Файл | Содержимое |
| --- | --- |
| `database.dump` | PostgreSQL custom-format: схема, данные, владельцы и ACL |
| `database-globals.sql` | Роли PostgreSQL, включая чувствительные данные аутентификации |
| `redis.rdb` | Проверенный снимок Redis, в том числе очереди BullMQ |
| `minio-data.tar.gz` | Весь остановленный том MinIO, включая `.minio.sys`, IAM и все бакеты |
| `configuration.tar.gz` | `.env`, Compose с override, deploy.sh, ключ Jitsi, существующие `/etc/nginx` и `/etc/letsencrypt` |
| `manifest.json` | Размеры, SHA-256, версии/образы контейнеров, время и длительность остановки |

Образы контейнеров, код, системные пакеты, внешние сервисы, сайт/frontend и почтовый
сервер в эту копию не входят. MinIO восстанавливается сначала с записанным образом;
внешние KMS/identity и распределённые конфигурации этим инструментом не поддерживаются.
Версионирование бакетов не требуется для копирования остановленного полного тома.

Каталог `/var/backups/oxus-backend` доступен только root (`700`, файлы `600`).
Архивы содержат секреты и персональные документы: не помещайте их в Git или чат.
Шифрование отдельным ключом и удалённое хранение на этом этапе не настроены.

## Хранение

Для каждого окружения отдельно оставляем последнюю успешную копию за каждый из
**7 последних дней с успешными копиями** и **одну последнюю успешную воскресную
точку** по времени Алматы.
Совпадающая ежедневная и еженедельная точка хранится один раз: до 8 разных точек.
При пропусках 7 успешных дней могут занимать больше календарной недели.
До первого успешного воскресенья отдельной еженедельной точки нет.

Очистка касается только точек этого инструмента после успешной новой копии и
проверки хешей всех сохранённых точек. Старые ручные копии и `oxus-release-*`
не затрагиваются. `.partial` и журналы `operations` сохраняются для диагностики;
они не очищаются автоматически и при повторных ошибках требуют проверки места.

## Установка

На Mac сначала выполнить безопасный preflight без изменений сервера:

```bash
ssh -o StrictHostKeyChecking=yes root@87.106.144.28 'python3 - preflight' \
  < deployment/backup/oxus_backup.py
ssh -o StrictHostKeyChecking=yes root@test.oxusedu.com 'python3 - preflight --environment test' \
  < deployment/backup/oxus_backup.py
```

После `PREFLIGHT_PASS` скопировать файлы из этого каталога в новый закрытый каталог
под `/root` на соответствующем сервере и выполнить там `bash install.sh production`
или `bash install.sh test`. Установщик проверяет
готовность повторно, устанавливает программу в `/usr/local/lib/oxus-backup`,
создаёт приватное хранилище и включает только таймер. Он не запускает копирование
и не останавливает API. Существующий другой вариант программы/units не заменяется.
Права действующих `.env`, Compose и ключа Jitsi сохраняются; для существующего
ключа допускается UID 1001 с точными правами `400`.
Стандартные имена файлов секретов из образа MinIO допускаются только при отсутствии
самих файлов. Реальные внешние KMS, identity/etcd и файловая конфигурация требуют
отдельного плана восстановления; содержимое секретов проверка не выводит.

Ниже команды для Production. На Test во всех именах units и параметрах заменить
`production` на `test`. Шаблоны units одинаковые на обоих серверах; включается
только экземпляр, соответствующий проверенному окружению.

Проверка расписания и состояния на сервере:

```bash
systemctl list-timers oxus-local-backup@production.timer --all --no-pager
python3 /usr/local/lib/oxus-backup/oxus_backup.py status --environment production
```

До первой ночи `last_success` будет `null` — установка не означает, что копия создана.
После первого запуска:

```bash
journalctl -u oxus-local-backup@production.service -n 30 --no-pager
python3 /usr/local/lib/oxus-backup/oxus_backup.py status --environment production
python3 /usr/local/lib/oxus-backup/oxus_backup.py verify --environment production
```

Ожидается `LOCAL_BACKUP_COMPLETE`, свежая дата `last_success`,
`recovery_required: false` и `LATEST_BACKUP_INTEGRITY_VERIFIED`.
Длительность остановки находится в `maintenance_seconds`.
Отправка уведомлений о сбоях пока не настроена: проверяйте эти результаты ежедневно.
`verify` проверяет SHA-256 и читаемость tar/gzip, а не полное восстановление.

Ручной `python3 /usr/local/lib/oxus-backup/oxus_backup.py run --environment production` немедленно
останавливает API и MinIO: использовать только в согласованное окно обслуживания.
Сервис systemd дополнительно ограничен стартом в 00:00–00:14 Алматы.

## Сбой и возврат сервисов

При обычной ошибке или SIGTERM/SIGINT программа пытается запустить те же исходные
контейнеры и проверить их здоровье. `ExecStopPost` повторяет возврат при прерывании
процесса. Контейнеры не пересоздаются; миграции и восстановление данных не запускаются.
После сбоя питания проверяйте API и состояние вручную: это не гарантия автоматического
возврата при любой аварии хоста. Не удаляйте `active.json` для обхода проверки.

Если `recovery_required` равен `true`, сначала проверьте состояние сервиса и контейнеров.
После завершения процесса бэкапа можно повторить только запуск исходных сервисов:

```bash
python3 /usr/local/lib/oxus-backup/oxus_backup.py recover --environment production
```

Если контейнеры были заменены deployment или не возвращается здоровье MinIO/БД/Redis,
возврат потребует разбора причины. Незавершённая копия не публикуется как успешная,
предыдущие точки сохраняются. Диагностика печатает фиксированные коды без секретов.

Чтобы выключить будущие запуски, не прерывая текущий бэкап:

```bash
systemctl disable --now oxus-local-backup@production.timer
```

## Восстановление

Восстановление всегда отдельная операция. Сначала — в изолированные новые контейнеры
и новые пустые тома, без подключения к работающим окружениям и внешним SMTP/SMS/платёжным API.
Сохранить исходную точку неизменной; проверить её манифест и хеши.
Использовать точку нужного окружения; не подменять Production данными или секретами Test.

1. Взять версии и digest образов из `manifest.json`, конфигурацию — из закрытого
   `configuration.tar.gz`. Не распаковывать его поверх работающего `/etc` или проекта:
   архив включает симлинки TLS/Nginx и секреты, пути требуют ручной проверки.
2. Создать чистый PostgreSQL совместимой версии с отдельным временным superuser,
   имя которого отсутствует в исходных ролях. Через `psql -X -v ON_ERROR_STOP=1`
   загрузить `database-globals.sql`, создать пустую БД с исходным именем и владельцем,
   затем загрузить `database.dump` через `pg_restore --single-transaction --exit-on-error`.
   Проверить данные, владельцев, ACL и таблицу миграций. Не использовать `--clean`
   для существующей Production БД.
3. При остановленном новом MinIO извлечь содержимое `data/` из `minio-data.tar.gz`
   в новый пустой том с сохранением UID/GID и режимов файлов. Сначала запустить
   записанный образ и проверить все бакеты, IAM и доступ приложения к документам.
4. Если требуется вернуть очереди, положить `redis.rdb` как `/data/dump.rdb` в новый
   том Redis, выставить владельца по используемому образу, проверить
   `redis-check-rdb`, затем запустить Redis совместимой версии.
   **Не запускать обработчики очередей до сверки заданий:** восстановленные задания
   могут повторно отправить письма, уведомления или выполнить другие внешние действия.
5. Проверить API с отключёнными внешними интеграциями и реальные связи БД ↔ документы.
   Только после этого планировать отдельное переключение Production.

Локальные тесты проверяют аварийные ветки, хранение и настоящее восстановление
синтетических данных PostgreSQL 16 и Redis 8. Это не заменяет пробное восстановление
конкретной Production точки; `restore_exercised` остаётся `false`.

```bash
python3 -m unittest discover -s deployment/tests -p test_backup.py -v
# Только Mac с Docker Desktop и уже загруженными postgres:16.0 и redis:8-alpine:
OXUS_BACKUP_INTEGRATION=1 python3 -m unittest discover \
  -s deployment/tests -p test_backup_integration.py -v
```
