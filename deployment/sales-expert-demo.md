# 36 лидов для Sales и Expert

Одна команда создаёт связанный набор для Sales и Expert, указанных аргументами `--sales-email` и `--expert-email`: 36 лидов, исходные анкеты, история, перезвоны, консультации, приглашения, онлайн-комнаты, уведомления внутри приложения и 3 демонстрационных договора с отдельными тестовыми учениками.

Это подготовленные состояния для проверки интерфейса. Дальнейшие действия фронтер выполняет обычными кнопками/API. Создание готового подписанного договора не доказывает прохождение OTP, оплаты или доставки документов.

## Распределение

При каждом запуске скрипт берёт **сегодня, завтра и послезавтра по Asia/Almaty**. В каждом из трёх дней по 12 сценариев. «День» обозначает дату задач/встреч или группу для проверки; у новых лидов и архивных карточек нет отдельного поля даты задачи. Даты создания и завершённая история остаются в прошлом. Будущие события не помечаются завершёнными.

| **Итого** | **12** | **36** |

Sales видит все 36: 33 назначены ему, 3 доступны в общей очереди NEW для принятия. Expert видит 24 связанных лида: 12 консультаций, 6 дожимов/переносов, 3 договора и 3 отказа.

Если на момент первого запуска некоторые консультационные слоты уже прошли, они получают COMPLETED / FOLLOW_UP и Lead RECALL. Поэтому фактическое число строк во вкладках NEW и FOLLOW_UP эксперта зависит от времени запуска; общее число связанных лидов остаётся 24. Приоритет отдаётся свободным будущим слотам, затем прошедшим. Не создаются просроченные REQUESTED-запросы или будущие завершённые консультации.

## Запуск после CI/CD

После попадания файлов в `main` обычный CI собирает команду в `dist/src/prisma/seed/run-sales-expert-demo.js`. Dockerfile уже копирует `dist` в образ. Дождитесь успешного деплоя версии с этим скриптом.

Предварительный просмотр на сервере (без записи в БД):

```bash
cd /opt/oxus_backend/deployment
sudo docker compose --env-file .env -f compose.yaml exec -T backend \
  node dist/src/prisma/seed/run-sales-expert-demo.js \
  --sales-email=sales@oxusedu.com \
  --expert-email=expert@oxusedu.com
```

Создание набора на сегодня и следующие два дня:

```bash
sudo docker compose --env-file .env -f compose.yaml exec -T backend \
  node dist/src/prisma/seed/run-sales-expert-demo.js \
  --sales-email=sales@oxusedu.com \
  --expert-email=expert@oxusedu.com \
  --apply
```

Дата начала вычисляется по моменту запуска в Asia/Almaty независимо от часового пояса сервера. Например, запуск 11 сентября создаёт задачи на 11–13 сентября, запуск 12 сентября — на 12–14 сентября. Ручной `--start-date` больше не поддерживается. Момент запуска фиксируется один раз, чтобы дата не менялась внутри выполнения при переходе через полночь.

Повторение для той же пары аккаунтов **в тот же день** сохраняет прогресс без дублей. Запуск в другой день или для другой пары создаёт отдельный новый набор из 36 лидов; предыдущий набор сохраняется, даже если диапазоны дат пересекаются. Если предварительный просмотр и `--apply` выполняются по разные стороны полуночи, запись использует уже новый день запуска. В маркерах используются ID аккаунтов, поэтому изменение email не дублирует набор в пределах того же дня.

Результат команды — JSON с фактическим диапазоном `startDate` / `endDate`, разрешёнными аккаунтами в `accounts` (email и ID), кодами S01–S36, ID лидов, статусами, временем новых встреч/перезвонов, числом созданных/сохранённых карточек и добавляемыми окнами расписания. Существующие сценарии выводятся с актуальными ID и статусами; их изменённое расписание смотрите в приложении.

Email проверяются и сравниваются без учёта регистра. Нельзя использовать один аккаунт для обеих ролей; отсутствующий пользователь, неверная роль или неоднозначное совпадение останавливают запись. Для совместимости со старой командой при пропуске флагов используются `sales@oxusedu.com` и `expert@oxusedu.com`; рекомендуется всегда указывать оба явно. Старые маркеры фиксированной пары также распознаются при повторном запуске для неё.

Команда использует серверные настройки контейнера. `STAGING` должен быть строго `true`; `NODE_ENV=production` на тестовом контейнере допустим. Для запуска через SSH необходим доступ к указанной Docker-команде: имеющееся разрешение `sudo deploy.sh` само по себе его не предоставляет. Отдельный GitHub workflow для заполнения не добавлен.

## Поведение при повторении и ограничения

- Существующие аккаунты сотрудников, роли и права не изменяются. Нужны активные Sales и Expert с CRM-правами, профиль эксперта, timezone Asia/Almaty, роль STUDENT и активные источники office-manual / landing-calculator.
- Если на нужный день недели совсем нет расписания, команда добавляет окно 09:00–17:30. Это **еженедельная доступность**, в том числе на выходных; она не ограничена только календарными датами набора. Предварительный просмотр показывает `schedulesToAdd`. Существующие окна не заменяются. Если в них не хватает слотов, команда завершается без записи.
- Маркеры набора сохраняются в LeadSubmission.externalSubmissionId, имя начинается с DEMO-Sxx. Повторение сохраняет прогресс, новые статусы, изменённые контакты и даже мягко удалённые карточки; оно не восстанавливает их и не создаёт дубли. Удалять маркеры вручную не следует.
- Создание всех отсутствующих сценариев проходит одной транзакцией с блокировкой бронирования эксперта. При ошибке новые лиды, договоры, ученики и добавленные окна расписания откатываются вместе. Другие лиды и существующие встречи не редактируются.
- Контакты синтетические: email на `example.invalid`, телефоны с тестовым префиксом `+999`. Три аккаунта учеников имеют случайный неизвестный пароль и предназначены для отображения связанных договоров. Скрипт не создаёт приглашения активации, не отправляет email/SMS и не создаёт задания доставки документов.
- Для настоящего клиентского входа, активации, OTP и подписания используйте отдельного контролируемого тестового клиента через обычный CRM-процесс. Договоры здесь — снимки состояний с демонстрационной ценой 250000 KZT, а не реальные подписанные документы.
- Будущие IN_APP-напоминания восстановит штатный обработчик очереди. Скрипт не запускает Nest-приложение и не рассылает WebSocket-события начального заполнения: после команды обновите страницы обоих кабинетов. Дальнейшие действия UI используют обычные уведомления и WebSocket.

## Проверка скрипта локально

Unit-проверки плана входят в обычный `yarn test`. Интеграционная проверка требует отдельной **пустой**, мигрированной локальной PostgreSQL с именем БД, заканчивающимся на `_test`:

```bash
yarn test:sales-demo
```

Передайте её `DATABASE_URL` через окружение. Проверка создаёт собственных сотрудников и демонстрационные записи. Она проверяет dry-run, связи, видимость через текущие сервисы Sales/Expert, занятые слоты, повторный и конкурентный запуск, сохранение прогресса, запуск скомпилированной команды с email-аргументами, изоляцию пар сотрудников, старые маркеры, изменение email аккаунта, позднее заполнение сегодняшнего дня и полный откат при ошибке в конце записи. Это не проверка фронтенда, реальной видеосвязи, почты или SMS.
